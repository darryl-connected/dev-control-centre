# Make DCC your own

DCC is a user-owned starter kit, not a policy for your personal Pi profile. Edit your own persona, instructions, skills, integrations and workflow. Use task preparation, ordinary Pi, your own workflow or the optional DCC factory. The shipped ClickUp adapter is read-only; write integrations and other omitted features are not shipped or verified, not forbidden extensions. Separately obtain authorization from the relevant system and repository owners. Your preferences do not change a target repository's rules, grant external access or change an already approved job. Changes to the kit itself may require rebuilding and reviewing its core; contributing changes to the upstream DCC repo follows its own `AGENTS.md`.

## Personal instructions and skills

Run [setup inspection](pi-setup.md) before applying anything. `--append keep-personal` (the default) never creates a project append. An existing project append is preserved, not disabled: when trusted it still takes precedence over the user append. To use your user append instead in that case, choose what to do with the existing project append yourself. To opt into the shipped template in a workspace with no project append, inspect using `--append use-template`, then separately approve the plan and acknowledge the shadow; the copied file is yours to edit. Pi does not merge the two appends. Other context files and Pi extensions can still affect the prompt.

If `.pi/settings.json` exists, setup leaves it byte-for-byte intact. Use the kit paths printed in `plan.skills` to add selected references yourself, or use the skills as documents without registration. On initial setup without settings, DCC proposes registering its shipped skills. Use `--no-skills` for mappings without registration. For a reported collision, `--skill-choice factory=keep` omits DCC's factory registration; `--skill-choice factory=register` chooses the kit skill. The plan names other affected resource paths and their scope. When creating new workspace settings, a known workspace-scoped collision can be excluded with an exact `-path` entry without deleting the file. To switch away from a user-scoped skill or change existing settings, disable just the affected entry in its own Pi scope (review `pi config` or the appropriate `skills` settings), add the kit entry as needed, and inspect again. Do not disable all your skills to resolve a single name. Inspect Pi's actual resource origins before relying on the result.

Setup doesn't evaluate extensions, install packages, resolve their dynamically supplied resources or interpret all Pi package, YAML and glob combinations. Advisory resources are not a readiness or safety finding. Review your resources before granting project trust. Malformed JSON at a setup destination, symlink destinations and stale approved plans stop application. Setup does not copy credentials or modify user settings or trust.

## Factory policy for new jobs

For the optional runner, copy the [credential-free example](../templates/dcc/policy.json) to your workspace's `.dcc/policy.json`, or omit it to use the shipped defaults. Specify that workspace with `factory-run.py preview --workspace /physical/workspace`, or run preview from it. Only `version: 1` is required; omitted role entries, allowance entries and repair limit use their defaults. Each overridden route supplies `provider`, `model` and `reasoning` together. Use exact Pi IDs, including case and any model namespace. Do not use aliases, fuzzy patterns or API keys. Reasoning accepts `model-default` (no Pi flag), `off`, `minimal`, `low`, `medium`, `high`, `xhigh` or `max`; choose a level supported by your Pi version and model. A writer and reviewer may use the same model in separate sessions and worktrees. They must not be the same session or worktree.

The defaults are DeepSeek Flash with model-default for the writer, and `openai/gpt-6.1-sol` with high reasoning for the coordinator and reviewer. Initial writer and reviewer get 60 calls/25 active minutes each, repair writer 30/15, re-review 40/20, with at most two repairs. Supply positive integer `calls` and `minutes` for each overridden attempt kind. `repair_limit` is a nonnegative integer, including zero to forbid repairs. An approved writer switch uses one repair allowance. The optional CLI attempt limits narrow the workspace values for just that job. Cumulative usage is reported; `--overall-limit CALLS:MINUTES` is a separate opt-in ceiling.

Set the manifest writer to the exact selected writer identity and worktree. Review the resolved policy, digest, exact identities, reasoning and limits in the preview before approving it. The runner records the coordinator route but does not launch or change the coordinator session; the developer verifies that session matches the selection. On approved launch, the runner checks the exact models in the approved Pi executable's offline inventory with the selected agent directory and any explicitly approved provider extension. It does not check authentication by making a provider request or prove that every effort level is effective. Check the actual session identities and thinking before relying on a role. No credentials belong in the policy, CLI arguments or evidence.

Keep the approved plan with state. Edits or removal of the workspace policy only affect new previews. Active commands verify the frozen plan and never repopulate allowances from the workspace. If records no longer match, preserve progress and seek explicit reapproval. Legacy active records are not migrated: keep their evidence and spent usage, finish with their original tooling if appropriate, or obtain explicit approval for a new job without pretending the old authorization or counters transferred. No automatic provider fallback, repair beyond the chosen limit, commit or push.

Portable local tests exercise files, policy, dispatch arguments and receipt bindings with deterministic fixtures. Custom provider/account combinations, arbitrary third-party resources, model behavior, and fresh-platform operation are not established by those tests.
