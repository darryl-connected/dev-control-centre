# Factory

You can invoke this skill with `/skill:factory`. Resolve all links relative to this skill directory. Read the repo-owned [coordinator](../../factory/COORDINATOR.md), [worker](../../factory/WORKER.md), [reviewer](../../factory/REVIEWER.md), and [factory contract](../../references/factory-contract.md). Use the shipped [factory job CLI](../../scripts/factory-job.py) and [alignment CLI](../../scripts/factory-alignment.py) for offline preparation and checks. No private or global factory installation is required.

This is an optional workflow for a developer who chooses the DCC factory. Your own workflows can coexist with it. Follow A1–A8 in the coordinator instructions, including requirement-derived observable outcomes, adversarial boundary checks, decision traceability, and honest limits on evidence. Preserve target repository rules and its engineering workflow. Record the named baseline, allowed paths, exact checks, approved budgets and stops. Keep one isolated writer per worktree and independent acceptance review in a distinct worktree. Keep the accepted handoff uncommitted.

The operating developer approves launch, provider switches, scope or budget changes, external or destructive actions, and commits. A ready verdict or green preflight is not launch approval. Do not launch agents or worktrees, switch providers, install dependencies, commit, push, publish or clean up from this skill without the developer's explicit approval for that exact action. Pause for the developer at the boundary; planning and review keep their approved models for the active job. The declared writer-only switch policy and a deterministic-provider fixture are not proof of live routing.

## Default for new jobs: coordinate directly

Follow the coordinator guide for the brief, role policy, budgets, review and handoff gates. Read the developer's workspace policy when selecting roles and limits, then record the exact selections in the contract before approval. Use the sequence below in place of its runner-specific preview, launch and advance commands. Do not load or enable the inbox, create an inbox registration or run `factory-run.py` on this path. Do not switch the mode of an existing job.

### Coordinator setup before launch

**Workspace and session.** If the conversation that clarified the job is already in the target repo's Herdr workspace, keep it as coordinator. If it is in another repo, propose a fresh Pi coordinator session rooted in the target repo, not a fork or resume of the original conversation. Show the destination workspace and planned full-size coordinator, writer and reviewer tabs before changing the layout. Use the target repo's existing workspace. If it is missing, ask the developer to open it or separately approve one-time workspace setup before the factory job. Opening a coordinator session requires approval and does not authorize writer or reviewer launch.

**Pi profile.** Use Pi's default profile if no override is selected. When the developer selected a different profile, pass its profile environment explicitly into the new Pi process (for example `PI_CODING_AGENT_DIR`, and `HOME` if the profile uses an isolated home). Do not assume a new Herdr tab inherits the current Pi process's environment. Confirm the effective agent directory from the destination session before sending a prompt. If the profile does not match, stop and diagnose the mismatch before suggesting sign-in. Do not read or copy credentials, change saved settings, or fall back to another profile. Profile selection does not change the approved model route or reasoning.

**Handoff and acknowledgement.** Give the fresh coordinator only the target repo, baseline if known, agreed scope and exclusions, evidence locations, approvals granted and still needed, and the next action. Do not transfer the full transcript or include credentials. Wait for a bounded time and require a reply from that session confirming it received the scope and knows the next action. A successful send or idle status is not acknowledgement. If sending stalls, inspect the intended destination to distinguish text still in the editor, submitted input, and an actual reply. If the text is visibly unsubmitted, submit it once rather than pasting again. Do not blindly resend. Until acknowledgement, keep the original session responsible for the handoff and pause the job. After acknowledgement, the fresh session is the coordinator; the original session stops coordinating that job.

### Job sequence

1. **Prepare and approve.** Snapshot the named baseline, run preflight and render the brief. Before launch, verify that this Pi session is in the existing Herdr workspace for the target repo and that the required tools and approved role routes are available. For a new job, verify the exact reviewer route has at least 1M tokens of context under the [coordinator role policy](../../factory/COORDINATOR.md#role-policy); block launch if it does not or the capacity is unknown. Show the developer the reviewer's context window, the exact brief, layout, report and receipt paths outside the target and role worktrees, and a finite wait for each role within its approved allowance. Explain that this conversation stays busy during each wait. Stop for explicit launch approval.
2. **Run and wait for the writer.** In that workspace, create a full-size writer tab with its own Git worktree. No new workspace or split pane. Launch a separate Pi session on the approved writer route, verify its identity and working directory, and submit the brief. Wait only on that agent with an explicit timeout. Read the writer's final message, report and evidence at the agreed paths. An idle or done tab is only a cue to inspect the report. If the role times out, blocks or leaves no valid report and candidate, stop and report the blocker; do not retry or dispatch review on that signal alone.
3. **Run and wait for independent review.** Record the exact candidate identity and verify the copied bytes and Git modes in a separate review worktree. Recheck the approved reviewer route and any context minimum bound for this job before dispatch. Launch the independent reviewer in another full-size tab of the same workspace on the approved reviewer route. Wait with the same bounded procedure and read the actual receipt and evidence. Advance between approved stages without a routine developer check-in. For in-scope repairs and re-review, use the existing repair limits, retain prior evidence and bind the new review to the revised candidate.
4. **Gate the handoff.** Recheck the unchanged target baseline and run `factory-job.py integration` with the exact candidate and approved receipt. Stop if the candidate or evidence is mismatched, missing or unapproved. Ask before staging; on approval stage only the accepted files, verify bytes and modes, and stop uncommitted. Ask separately before cleanup.

The developer can open another conversation for unrelated work without moving this job. The manual same-workspace flow on macOS is NOT VERIFIED until rehearsed end to end.

## Optional: use the runner

The coordinator-invoked loop is available locally through [factory-run.py](../../scripts/factory-run.py). Use it only if the developer explicitly chooses and approves the runner path for a new job. Follow the runner sequence in the coordinator guide, including [inbox setup](../../docs/factory-handoff.md). The runner still requires inbox records; it is not an inbox-free command. The adapter only notifies; it does not grant approval.

Record exact observations, exits, and skips. These instructions, offline gates and synthetic loop tests do not establish model obedience, process isolation, authenticated provider operation or fresh-platform success.
